## 正しい項目を開く

既存項目の修正では、目的の本文言語で項目を開き、リーダーの編集入口を使います。編集画面には実際のソースパスが渡されます。新規作成では[投稿ページ](/ja/contribute/)から[項目エディター](/ja/contribute/editor/)へ進み、上部の「ファイル」メニューで新しい項目を選び、エンティティの種類と原文言語を指定します。簡体字中国語、日本語、英語が編集する原稿です。台湾・香港の繁体字は簡体字から生成されます。

リーダーの「この項目を改善」、追記待ちの案内、整備状況の不足項目も同じ項目のエディターを開きます。別の投稿経路ではありません。[百科の一覧](/ja/database/)の新規作成からも進めます。検索結果がなくても、先に条件を消して別名を調べ、重複する項目を作らないでください。

## 不足資料を見つける

[資料整備ボード](/ja/contribute/missing/)には構造化された項目が未記入の記事が並びます。名前・別名を検索し、記事の種類と不足項目を組み合わせたり、出典・クレジット・画像のボタンから探したりできます。24 件ずつ表示し、条件を URL に保存します。「資料を追記」は実際の原稿を開きます。翻訳が不足している場合は現在の原文言語を確認し、多言語の翻訳手順を使ってください。

ボードとリーダーは同じ充足率の規則を使います。仮画像は記入済みとせず、公演ではセットリストを確認しますが、展示には求めません。点数は記入状況であり、事実と出典は別途確認が必要です。審査・マージ・サイト更新の完了後に公開ボードへ反映されます。

## 本文と属性

執筆時には[内容と形式の完全ガイド](/ja/docs/contribute/format/)も確認してください。構成、名称、文体、出典、日時、メディア、プライバシー、多言語、項目種別ごとの骨格、提出前チェックまで、元の詳しい規則を収録しています。Markdown、frontmatter、媒体構文、フィールド例は[構文と属性の完全ガイド](/ja/docs/contribute/syntax/)にあります。この二冊の詳細を本章の短い説明で置き換えるものではありません。

重複を避けるため別名も検索してください。新しい安定 ID は英小文字、数字、ハイフンで作り、言語間で共有します。表示名が変わっても ID は変えません。種類に応じてエディターが示す必須属性を埋め、本文を書きます。表紙、関係、出演者、制作クレジットなどは「項目の属性」に入力します。ページ URL をソースファイルのパスと混同しないでください。仮項目も確認済みの情報と出典を記載し、推測で空欄を埋めません。

並列プレビューとアウトラインで見出し・目次・アンカーを確認できます。挿入ボタンまたは `/` メニューで内容を追加し、拡張構文はソース表示で保持します。既存項目の正しい事実、引用、不明な構文をむやみに削除しないでください。提出前に差分、画像、関連、出典を確認します。

## 画像と添付

項目の本文は **GitHub PR**、新しい画像は **画像ライブラリ** で審査します。それぞれ別の投稿記録になります。

1. エディター内または[画像ライブラリ](/ja/media/)を開きます。公開済み画像はそのまま再利用できます。
2. 新しい画像は本文用画像を選び、作者・出典・利用根拠を記入してアップロード・提出します。PNG/JPEG/WebP/GIF、100 枚まで、1 枚 20 MiB。一時保存だけでは公開されません。
3. [クリエイターセンター](/ja/account/creator/)で画像ごとの意見を確認します。差し戻し後も一時保存済みファイルを使って再提出できます。承認後に本文へ挿入するかカバーに設定します。
4. 本文には公開画像 URL を保存します。本文 PR で画像を再アップロードせず、本文は審査・マージ・デプロイを経て公開します。

未完了のアップロードはアカウント別に端末へ保存し、再読み込み後に明示的に復元できます。保存に失敗した場合はページを閉じないでください。以前の下書きの添付と既存の /images/ 参照は引き続き利用できます。

## 確認と提出

必須項目、根拠、プレビュー、関連、言語、変更理由を確認します。ログイン済みで投稿サービスが利用できる場合、上部の**GitHub PR で投稿**を使い、受付記録を保管してください。投稿停止の表示がある場合は、ローカル保存を投稿完了と見なさず、下書きの保存または書き出しを行います。審査、GitHub マージ、サイト更新が完了して公開項目に反映されます。差し戻しは[審査の説明](/ja/docs/contribute/review/)を参照してください。

## メタデータが表示を決める

旧貢献ガイドのフィールド一覧は V3 でも有効です。`schemaVersion: 2` は**メタデータの規約番号**であり、サイトの V3 とは別です。エディターで項目の種類を選び、その種類に必要なフィールドを記入します。本文に名前を書くだけでは構造化された関係は作られません。

| フィールド | サイトでの用途 | 投稿前の確認 |
| --- | --- | --- |
| `id`、`locale`、`entityType` | 言語をまたぐ識別と正規 URL | 三つの原文言語で同じ ID を使い、別の実体の ID は再利用しない。 |
| `name` または `title` | 見出しと一覧の名前 | 確認できる正式名称を使い、訳名は分けて示す。 |
| `presentation.image`、`presentation.theme` | 表紙、リーダーの背景、局所テーマ | 画像 URL を開いて確認する。色は事実の根拠にはならない。 |
| `presentation.morphing` | 画像と名前の形態切替 | 同一系譜の独立した項目にだけ使う。 |
| `classification.primary`、`classification.additional` | 正規分類と追加の発見経路 | 追加分類のために本文を複製しない。 |
| `relations`、`performers`、`credits` | 関連項目と逆引きクレジット | 安定した対象 ID と正しい関係種別を使う。 |
| `sources`、`license` | 出典と文章の利用条件 | 文章のライセンスは画像の利用許諾ではない。 |
| `contentStatus`、`lifecycle` | 仮項目と活動状態 | 不明な日付を推測で埋めない。 |

[分類の保守ガイド](/ja/docs/develop/content/)と現在の分類データを確認してください。一つの実体は複数の分類から見つけられますが、言語ごとの本文と正規 URL は一つです。ユニットの新しいメンバーにはユニット項目と実際の `member-of` 関係が必要で、メンバーだからといって個人階層へ自動配置しません。楽曲の歌唱者は `performers`、制作は `credits` を使います。正規分類や元ファイルの変更には旧 URL の転送確認が必要です。

## サイト内添付の上限を超える原本

新しい画像は[画像ライブラリ](/ja/media/)へ投稿します。1 枚が 20 MiB を超える場合は管理者に相談し、本文 PR に大きな画像ファイルを直接追加しないでください。手動の GitHub 投稿では、承認済みの公開画像 URL を Markdown から参照し、作者・出典・利用根拠を残します。既存の public/images/ ファイルは /images/ URL を維持し、移動や削除は不要です。

## 提出前チェックリスト

- 別名と他言語版を検索し、主分類を詳細マップと照合する。
- 事実、日付、引用、画像に確認可能な出典を付け、不確実な点を明記する。
- 正しい旧本文、未知の拡張構文、出典を残し、差分で誤削除を確認する。
- 目次、アンカー、画像 URL、関連 ID、言語間の同一性をプレビューする。
- 受付番号を控え、表示されない場合は Creator Center を確認してから再投稿する。
