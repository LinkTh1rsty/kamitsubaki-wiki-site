## 这篇教程怎么用

第一次投稿，可以按本章从头做一遍；已经会操作，只需用目录跳到卡住的步骤。这里以“给现有词条补充一条有来源的活动信息”为演练。示例**不提供虚构的活动日期或公告网址**：请在自己的投稿中填入真实资料。旧版指南提出的“选择路线 → 找到源文件 → 按需查语法 → 预览差异 → 提交 PR → 跟进检查与审阅”仍是这篇教程的骨架。网站现在又提供站内投稿，因此每一步都列出两条路线的对应操作。

### 先备齐四样材料

1. **目标页面。** 在[百科资料库](/zh/database/)搜索名称和别名，打开当前语言的词条；从页面地址确认这就是要修的实体。不要看到筛选结果为空就直接新建。
2. **原始资料。** 保存官方公告或其他可核对页面的标题、发布者、网址、发布日期和与你要写的事实直接对应的段落。截图可以辅助辨认，但尽量附原始可访问链接。
3. **要改的一句话。** 先写清“哪一句原文、要改成什么、为什么”。若资料只给月份，就写月份，不补具体日期。把事实与推测分开。
4. **素材权利。** 若没有图片来源和使用依据，先只改文字。文字许可不自动覆盖封面、照片、歌词和视频；请看[来源与授权说明](/zh/docs/contribute/rights/)。

## 第一步：从目标词条进入

打开目标词条的阅读页，先读正文和“参考资料”，确认没有人已经补过同一信息。点击“完善此词条”或“编辑源文件”进入编辑器，确认页面顶部显示的实体、语言和源文件是你打算修改的对象。若要创建新词条，先到[投稿选择页](/zh/contribute/)选“百科词条”，在编辑器中选择实体类型和原文语言；同一实体的中文、日文、英文源稿使用同一稳定 ID。台湾和香港繁体由中文源稿生成。

通过 GitHub 投稿时，从词条页的源文件入口进入仓库，核对路径通常位于 `src/content/` 下。不要编辑 `dist/`、`.astro/` 或 `node_modules/`。旧版人物词条的分节思路仍适用：概述、角色与创作定位、活动历程、代表作品、相关企划、参考资料、外部链接。实际栏目要跟随实体类型与现有正文，修订时保留已有可靠信息。

## 第二步：只改资料支持的内容

编辑器会带入现有内容。先选语言，再在合适段落增补事实；日期、关联对象、制作署名等结构化属性应填在对应字段，不要只藏在正文。原文已有引用或扩展语法时，先理解再改。内容结构、分类、文风和来源规则见[完整内容格式指南](/zh/docs/contribute/format/)；Markdown、属性、注音、折叠内容、媒体短语法与歌词排版示例见[完整语法指南](/zh/docs/contribute/syntax/)。

例如，资料只证实“某企划在 2026 年 9 月公布一项活动”，写作时可以保留“2026 年 9 月”；不能改写成 9 月 1 日。活动名称、成员、地点也只能写来源实际提到的内容。引用要放在事实附近，参考资料中保留资料标题和原始网址。要表示“尚待查证”，明确写出待核对点，不用空白或猜测填满条目。

**词条附件与图片档案是不同流程。** 词条正文或封面的附件随词条提案进入 GitHub PR；图片档案可以[直接投稿独立照片，也可以创建设定组](/zh/docs/contribute/gallery/)，不必先给每张照片分类。每张图仍须填写可核对的作者、出处和使用依据。不要把一套设定图当作词条附件上传。给资料页选择局部主题色时，先从官方主视觉或角色稳定识别色取依据；缺少依据就保留默认样式，界面主题色不会改变图片原色。

## 第三步：用预览和差异自查

在编辑器打开预览，对照阅读页检查标题层级、目录锚点、图片、链接和引用。再查看变更差异，确认只改了这次有意修改的段落。**保存本机草稿不等于提交审核**；在草稿仍在时可以继续查证。若网络断开，先导出或复制草稿，再刷新页面。

GitHub 路线请在自己的分支或 Fork 中修改目标文件，检查 YAML frontmatter 的引号与缩进，确认 `id`、`locale`、`entityType` 等身份字段没有意外变化。新增同一实体的多语文件时要保持 ID 一致。运行仓库的 `pnpm test`、`pnpm check`、`pnpm build`；在 PR 的 Files changed 中再次看差异。构建失败应读实际错误行，不要盲改不相关文件。

## 第四步：提交与审阅

站内路线点击“提交审核”后，等到页面给出记录编号或 PR 链接，再到[创作者中心](/zh/account/creator/)确认状态。若只看到“保存成功”或“文件已暂存”，投稿尚未进入审核。提交超时先查是否已有记录，再决定是否重试，避免重复提案。管理员要求修改时，打开**同一条投稿**，对照意见修订并再次提交。

GitHub 路线则创建 Pull Request，写清目标词条、事实来源、修改理由及本地检查结果。在同一 PR 中回复审阅意见并推送修订。GitHub 投稿不一定自动出现在站内创作者中心，进度以该 PR 为准。CI 通过、管理员审阅通过、PR 合并和网站发布是不同节点。最终打开公开词条，核对修订已经出现；时间轴修订还要确认公开事件版本。

## 另一类投稿怎样套用

| 投稿类型 | 先准备什么 | 在哪里检查结果 |
| --- | --- | --- |
| [文章](/zh/docs/contribute/article/) | 明确论点、作者、来源和关联词条 | 文章预览、审核记录、公开文章页 |
| [图片档案](/zh/docs/contribute/gallery/) | 每张图的作者、出处和使用依据；人物、类型、标签和设定组可后补 | 私有暂存、逐图审核、分类建议、公开图片 |
| [时间轴](/zh/docs/contribute/chronicle/) | 日期精度、轨道、关联词条、至少一项原始来源 | 事件预览、PR 审核、公开事件版本 |

时间轴中的单日事件是一个时间点，持续事件的长度由真实日期跨度决定。只知年或月时保留不确定区间。新增与修订都可以从编辑器起稿；在 GitHub 路线，新事件使用独立 YAML 文件，修订只改目标事件。

## 把 AI 当成校对助手

把你已经收集的资料交给 AI，请它整理结构、检查缺口；**它不能代替来源，不能凭空补日期、人物、授权或翻译**。可复制下面的提示词，把方括号内容替换为你自己的资料：

> 我正在给 KAMITSUBAKI Wiki 的 [词条名称与语言] 补充 [要改的事实]。请只根据我粘贴的原始资料，列出：①可直接确认的事实及其对应原文；②日期精度（年／月／日，资料没有的不要猜）；③还需核对的信息；④建议放入词条哪个段落。请保留原资料标题和网址，不要编造来源，不要替我判断图片授权。资料如下：[粘贴来源标题、网址和相关摘录]

> 下面是我修改前后的两段文字及来源。请逐句指出：哪些主张在来源中找不到、哪些引用离事实太远、是否误删原文有效信息、是否把推测写成事实。不要直接新增事实。修改前：[粘贴] 修改后：[粘贴] 来源：[粘贴]

得到建议后，请**逐项回到原始页面人工核对**。歌词、译文、图片署名和时间戳尤其需要自己复查。旧版歌词 AI 排版提示词与站内扩展语法示例保留在[完整语法指南](/zh/docs/contribute/syntax/#ai-lyrics-html)。

## 提交前最后检查

- 搜索过名称与别名，确认没有重复词条或同一事件。
- 每条新事实有对应的原始来源；日期精度与资料一致。
- 原有正确正文、引用和不熟悉的扩展语法没有被误删。
- 图片、歌词及第三方文字的授权边界已经核对。
- 预览中的标题、图片、链接和目录能正常使用。
- 站内收到了投稿回执，或 GitHub 上确实创建了 PR；保存草稿不算投稿。
- 合并之后还会核对公开页面，未发布前不写“已公开”。
